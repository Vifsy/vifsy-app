# Spreelo v144.57.1 — weekly schedule QA hardening

This is the reviewed follow-up to v144.57. It keeps the weekly schedule manager design and fixes issues found during a second deep source review before production deployment.

## Fixes found in the second QA pass

- The alternate/legacy planner view can no longer bypass the weekly weekday model with a free date picker. Weekly posts are moved through the weekly rhythm instead.
- Past calendar-campaign rows are locked consistently in both planner views, show 0 credits and cannot be edited, duplicated, removed or unlocked.
- User-selected weekly weekdays are preserved by generic smart-rescheduling helpers.
- One-time/manual scheduling now also blocks a time earlier today, not only earlier dates.
- Added the missing UI labels for past-date and past-time validation.
- The worker now limits override retrieval to the base-date window actually relevant to the current candidate rules, so a large number of future overrides cannot push the active override outside the query cap.
- A weekly occurrence that has already started generating is locked even when that occurrence was previously moved to another day by an override. The API checks both the base schedule date and the current effective override date.
- Future automatic content types are explicitly described as a current Spreelo recommendation that may still adapt before generation, rather than being presented as a guaranteed frozen selection.
- UI translation cache bumped to v24.

## Database/security hardening

The migration remains `supabase/v144_57_weekly_schedule_overrides.sql`, but the corrected migration is safer than the first v144.57 draft:

- schedule overrides now have a foreign key to `automation_rules` with `ON DELETE CASCADE`, so deleted recurring rules cannot leave orphan override rows;
- orphan rows are cleaned before the foreign key is installed, making the corrected migration safe to run after the first v144.57 draft;
- authenticated customers retain read access to their own overrides, but direct authenticated INSERT/UPDATE/DELETE policies are removed;
- all override mutations are server-mediated after the recurring-plan API has verified rule ownership;
- the reservation-adjustment RPC remains service-role only.

If the original v144.57 SQL was already run, run the corrected SQL from v144.57.1 once more. It is intentionally written to repair the existing table/policies safely.
